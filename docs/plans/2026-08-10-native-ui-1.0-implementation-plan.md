# Native UI 1.0 Implementation Plan

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** Build a popular-ready, framework-independent UI system that makes ordinary semantic HTML attractive, adaptive, accessible, and practical with minimal authored CSS and optional JavaScript only for genuine interaction gaps.

**Architecture:** Native HTML owns meaning and native state; a classless CSS foundation owns visual quality; intrinsic CSS and container queries own adaptation; explicit compositions cover abstractions HTML cannot express; a small progressive runtime owns only compound interaction state; and a deterministic authoring analyzer reports opportunities, defects, and unnecessary code. One manifest governs every public selector, attribute, event, export, recipe, analyzer rule, compatibility requirement, and byte budget.

**Tech Stack:** Semantic HTML, modern native CSS, dependency-free ES modules, Node.js 22.14+, Node test runner, Playwright, axe-core, JSON Schema, GitHub Actions, npm trusted publishing, and static documentation.

## 1. Execution model and failure containment

This plan uses a specification-anchored workflow based on GitHub Spec Kit's current `specify → plan → tasks → implement` model, with clarification, checklist, and cross-artifact analysis gates before implementation. Large work is split into independently verifiable slices so an agent never needs the entire project context to complete one task.

### Sources used to design this workflow

- [GitHub Spec Kit](https://github.github.com/spec-kit/) — specification-driven phases and structured artifacts.
- [Spec Kit: handling complex features](https://github.github.com/spec-kit/concepts/complex-features.html) — bounded sub-specs and focused context.
- [Spec Kit: agentic SDD](https://github.com/github/spec-kit/blob/main/docs/reference/agentic-sdd.md) — read-only consistency analysis and convergence loops.
- [GitHub repository health files](https://docs.github.com/en/communities/setting-up-your-project-for-healthy-contributions/creating-a-default-community-health-file) — contributor-facing repository structure.
- [GitHub pull-request standardization](https://docs.github.com/en/pull-requests/reference/managing-and-standardizing-pull-requests) — templates, ownership, rulesets, and protected checks.
- [OpenSSF Best Practices](https://openssf.org/projects/best-practices-badge/) — open-source quality and security readiness.
- [npm trusted publishing](https://docs.npmjs.com/trusted-publishers/) — OIDC publication and automatic provenance.
- [Google SRE canary releases](https://sre.google/workbook/canarying-releases/) — staged exposure, comparison, and reversible rollout.
- [Semantic Versioning](https://semver.org/) — precise public API and immutable releases.

### Mandatory gates

Every implementation slice follows:

```text
requirement
→ failing contract/behavior test
→ minimum implementation
→ focused test
→ complete test suite
→ visual/manual evidence where required
→ documentation and manifest synchronization
→ focused commit
```

Do not begin a dependent task while its prerequisite gate is red. Do not weaken a test to make implementation pass unless the requirement itself is corrected first.

### Stop conditions

Stop and resolve evidence before continuing when:

- a behavior producer or consumer cannot be traced;
- browser support or accessibility behavior is uncertain;
- no-JavaScript fallback blocks the core task;
- a proposed selector, attribute, event, or export is absent from the manifest;
- a change exceeds the size budget without an approved tradeoff;
- analyzer output is nondeterministic;
- visual improvement breaks semantics, keyboard operation, zoom, forced colors, or reduced motion;
- generated upstream code would enter production without manual curation;
- package contents differ from tested artifacts;
- a release cannot be rolled back by restoring the previous immutable version/dist-tag.

### Recovery rules

- Keep each task in a small commit; correct failures with a new commit rather than rewriting shared history.
- Preserve the last passing implementation until the replacement passes all boundary tests.
- Use `next` prereleases before `latest`; never replace published package contents.
- Keep release workflows manual/staged until trusted publishing, provenance, and branch rules are verified.
- Record unresolved tradeoffs in an ADR and leave the dependent task blocked.

## 2. Fixed product decisions

These decisions are settled for 1.0 and must not be re-decided during implementation.

### Product and package

- Product name: **Native UI**.
- Canonical local repository: `/Users/faka/code/projects/web/native-ui-next` during clean-room development.
- Planned public repository: `github.com/IFAKA/native-ui`.
- Planned npm package: `@ifaka/native-ui`; the unscoped `native-ui` name is occupied by an unrelated package.
- License: MIT.
- Runtime dependencies: zero.
- Framework bindings: deferred until after 1.0.

### Public runtime API

```json
{
  ".": "./dist/native-ui.css",
  "./behavior.js": "./dist/behavior.js",
  "./manifest.json": "./dist/manifest.json"
}
```

### Authoring API budget

- Five layout classes: `nui-container`, `nui-readable`, `nui-stack`, `nui-cluster`, `nui-grid`.
- Default native actions need no variant.
- Three explicit action variants: `primary`, `danger`, `quiet` through `data-variant`.
- Classes are allowed only for non-native reusable compositions such as `.card`, `.badge`, `.toolbar`, or `.empty-state`.
- Ambiguous compound behavior uses `data-nui="tabs|menu|combobox|…"`.
- `data-nui-enhance="off|force"` controls enhancement.
- Public design tokens use the `--nui-*` prefix.
- No `.btn`, `.input`, `.dialog`, Tailwind utilities, generated state classes, or compatibility aliases.

### Visual direction

Use a restrained modern system aesthetic rather than raw UA styling or shadcn imitation:

- system fonts and platform-aware controls;
- grayscale-first hierarchy with one configurable accent and a semantic danger color;
- readable typography and consistent vertical rhythm;
- subtle surfaces, borders, radius, and shadows;
- 44px targets and 16px mobile controls;
- coherent light/dark mode, forced colors, contrast, and reduced motion;
- motion only for feedback, state, or spatial continuity, normally under 300ms.

### Smart-system boundary

- CSS automatically infers presentation from semantic elements, attributes, states, relationships, available space, and user preferences.
- JavaScript never calculates ordinary responsive layouts or injects styling classes.
- The browser runtime enhances only unambiguous native patterns or explicit `data-nui` patterns.
- The CLI is deterministic and explainable; it never runs AI or silently rewrites source.
- Application data, business rules, routing, analytics, and product branding remain outside Native UI.

## 4. Final acceptance matrix

### Product value

- Ordinary semantic HTML looks intentional with one stylesheet.
- Forms require no component classes.
- Real pages are attractive enough that beta users choose to keep the defaults.
- Authors can override tokens, CSS, compositions, and enhancement without fighting specificity or generated DOM.

### API and size

- One CSS import and one optional behavior import.
- Exactly five general layout classes and three action variants.
- Zero browser runtime dependencies.
- Combined CSS and optional behavior ≤ 12,288 bytes gzip.
- Basecoat-equivalent benchmark pages use at least 60% fewer authored class tokens.
- Every public symbol is manifest-backed, documented, and tested.

### Responsive quality

- One DOM across viewports.
- No JavaScript for ordinary layout, breakpoints, styling, or native-state mirroring.
- 320px, 200% zoom, long content, localization growth, coarse pointers, and dynamic viewport changes remain usable.
- Tables and dense regions expose deliberate, labelled overflow rather than clipping content.

### Behavior and accessibility

- Core content/actions remain usable without JavaScript.
- Compound widgets pass their APG/native keyboard, focus, state, and announcement contracts.
- Enhancement is idempotent, dynamic-DOM safe, cleanup-safe, and failure-tolerant.
- Forced colors, contrast preference, dark mode, reduced motion, and visible focus pass.
- No ARIA is used to repair an incorrect native interaction model.

### Analyzer

- Text/JSON output is deterministic.
- Findings include stable ID, location, severity, explanation, evidence, and recommendation.
- Ambiguous intent is reported, never silently resolved.
- Analyzer size/dependencies do not enter browser runtime budgets.

### Repository and release

- Community health files and contribution paths are complete.
- Protected checks, security scanning, dependency review, and CodeQL pass.
- Packed artifacts match tested artifacts.
- npm publication uses OIDC trusted publishing and provenance.
- Releases are immutable, semantically versioned, staged through prerelease tags, and reversible through dist-tags.

## 5. Assumptions and deferred work

- Modern evergreen browsers are targeted; exact versions are fixed by evidence before beta.
- Browser-native rendering differences are acceptable when hierarchy, usability, and accessibility remain coherent.
- The analyzer is deterministic development tooling, not runtime AI.
- Basecoat is the primary capability/visual reference; upstream projects never become runtime dependencies.
- React, Vue, Svelte, Web Components, design-tool plugins, automatic source rewriting, arbitrary React/Tailwind conversion, and product-specific templates are post-1.0 work.
- Popularity cannot be guaranteed. The repository is optimized for adoption through a clear promise, excellent defaults, tiny API, trustworthy evidence, welcoming contribution flow, secure releases, and fast first success.
